# AI Project Meta Method v3.0

## 面向长期项目的人—多 Agent 角色化协作元方法

- 版本：v3.0
- 日期：2026-07-23
- 状态：正式版本
- 适用范围：由一个项目所有者与一个或多个 AI Agent 长期共同维护的软件、研究、
  内容或混合型项目
- 核心变化：角色与 Agent 品牌彻底解耦；新增默认通用身份、执行器适配层、显式
  运行清单，以及同一执行器承担不同角色时的隔离规则

---

## 1. 为什么需要 v3.0

早期多 Agent 项目常把不同 Agent 当作“能力相近的独立帮手”。它们进入同一个
仓库、读取同一份项目记忆、以相同身份修改项目。实践中，这种方式通常没有形成
真正分工：

- 每个 Agent 都需要重新理解同一项目；
- 多个 Agent 使用同一身份，职责和交付物没有差异；
- Agent 的工作习惯不同，容易造成结构、风格和决策反复；
- 为避免冲突，多个 Agent 又不能安全地同时修改同一工作区；
- “用了多个 Agent”并不自动带来更高效率或更高质量。

v2.0 引入了实现者与审查者的串行闭环，解决了职责重复、缺少独立验收和无限循环
的问题。但参考实现仍容易把角色写成产品品牌：

```text
Claude = 实现者
Codex = 审查者
```

这会产生新的限制：

- 更换模型或 CLI 等同于重写项目身份规则；
- 不能自然地交换角色；
- 不能明确表达“同一种 Agent 在不同调用中承担不同身份”；
- Agent 直接进入项目时会被入口文件误判为专用身份；
- 不同 CLI 的权限机制不同，简单替换命令并不安全；
- Git 历史只显示“实现/审查”，却不一定能回答实际由谁、用什么模型完成。

v3.0 因而把一次 Agent 工作拆成五个独立维度：

```text
调用身份 = 角色契约 + 执行器 + 运行配置 + 权限配置 + 任务边界
```

角色说明“负责什么”，执行器说明“由谁运行”，适配器说明“怎样把角色约束落实到
该 CLI”，运行清单则说明“这一次实际上发生了什么”。

## 2. 核心原则

### 原则一：项目所有者保留目标权

人负责：

- 提出目标和阶段优先级；
- 决定范围、产品取舍和主观验收；
- 选择专用角色使用的执行器、模型和强度；
- 决定是否启动、停止或重新配置自动循环；
- 处理凭据、费用、部署、外部授权和不可逆操作。

Agent 可以提出证据和建议，不能自行改变项目最终目标。

### 原则二：角色不等于 Agent 品牌

`IMPLEMENTER`、`REVIEWER` 是职责；`claude`、`codex` 是执行器。两者必须独立配置。

不写：

```text
Claude 永远负责实现，Codex 永远负责审查。
```

应写：

```text
本轮 IMPLEMENTER 使用 claude/sonnet/high；
本轮 REVIEWER 使用 codex/gpt-5.6-sol/high。
```

下一轮可以交换，也可以使用同一种执行器。

### 原则三：未分配专用角色时默认 GENERAL

Agent 进入仓库，不应仅凭自己的产品名称推断身份。没有所有者或父脚本的明确角色
分配时，它是 `GENERAL`：

- 直接协助所有者完成当前明确任务；
- 不自动写实现/审查正式交接；
- 不推进自动轮次；
- 不把普通意见冒充正式验收；
- 不自行切换成专用角色。

这使普通维护、方法论改造、问题讨论和一次性基础设施工作不再被错误塞进自动循环。

### 原则四：专用角色是一次调用的临时身份

`IMPLEMENTER` 或 `REVIEWER` 只对本次进程有效。进程结束，身份结束。下一次调用
必须重新显式分配角色和配置。

### 原则五：执行器差异必须由适配层处理

不同 CLI 在以下方面不会完全相同：

- 模型和 effort 参数名；
- 只读/可写 sandbox；
- 工具白名单与禁止列表；
- 非交互批准策略；
- 最终消息输出方式；
- 会话持久化；
- MCP 注册与健康检查；
- 网络、缓存和工作区边界。

统一角色契约不意味着使用完全相同的命令。项目必须提供薄适配层，把相同角色意图
翻译成各执行器真正支持的安全参数。

### 原则六：实现与审查严格串行

同一工作区中，任何时刻最多只有一个专用 Agent 运行。父脚本等待当前进程结束、
验证交接和 Git 状态后，才启动下一进程。

Agent 不相互递归启动。交接由中立父脚本完成。

### 原则七：事实、目标、角色、状态分层

不同信息必须有不同唯一来源：

| 信息 | 推荐来源 |
| --- | --- |
| 当前项目事实 | `PROJECT.md` |
| 正式目标和验收 | `PROJECT_SPEC.md` |
| 共用身份协议 | `AGENT_PROTOCOL.md` |
| 角色职责 | `.agent/roles/*.md` |
| 审查等级和报告格式 | `REVIEW_CONTRACT.md` |
| 当前执行切片 | `.agent/next-task.md` |
| 默认运行策略 | `.agent/runtime.env` |
| 当前轮次状态 | `.agent/state.env` |
| 本次实际调用 | `.agent/artifacts/runs/*.env` |
| 最近实现交接 | `.agent/implementation-report.md` |
| 最近正式审查 | `.agent/latest-review.md` |

不要让聊天记录、旧计划和多份 README 同时争夺目标解释权。

### 原则八：自动化必须有终止条件

自动循环不是“持续到满意”，而是有限状态机。必须有最大轮数、PASS、流程错误、
重复问题、产品决策和不可验证等停止条件。

## 3. 三种角色

## 3.1 GENERAL：默认通用身份

适用场景：

- 所有者与 Agent 直接讨论项目；
- 梳理目标、解释代码、诊断问题；
- 修改协作基础设施或方法论；
- 所有者明确授权的一次性业务工作；
- 尚未准备进入正式实现—审查循环。

GENERAL 的权限由当前任务决定，不意味着全权。它的关键边界是：

- 不自动承担正式实现报告或审查报告；
- 不推进 `.agent/state.env` 轮次；
- 不自行启动其他 Agent；
- 不把自己的普通检查标成独立正式审查。

## 3.2 IMPLEMENTER：专用实现身份

职责：

- 按正式规格和本轮切片完成实现；
- 优先处理正式审查的 Blocker/Major；
- 更新相关测试和实现文档；
- 运行统一验证和需要的浏览器检查；
- 更新实现报告；
- 在完成一轮后停止。

边界：

- 不修改角色协议、审查契约、权限策略、轮次状态或历史审查；
- 不拥有 Git stage、commit、push、deploy 权；
- 不改变产品目标或降低验收标准；
- 不启动下一位审查者。

中立包装器在实现进程结束后检查 Git 历史、refs、索引、受保护路径、实现报告与
验证结果，再创建本地实现检查点。

## 3.3 REVIEWER：专用独立审查身份

职责：

- 对明确目标提交和基准进行独立检查；
- 核对正式规格、功能、回归、异常状态和测试；
- 使用可重复证据而非主观偏好；
- 对网页修改做实际浏览器验证；
- 输出固定格式、机器可校验的正式报告；
- 只给解决方向，不直接修复。

边界：

- 新进程、无实现会话继承；
- 只读权限、非交互批准；
- 不修改仓库或 Git；
- 不增加规格外需求；
- Minor/Suggestion 不得无限阻断完成。

报告安装、归档、状态更新和本地审查检查点都由父脚本执行。

## 4. 身份分配协议

推荐优先级：

1. 所有者在当前调用中的最新明确指定；
2. 父脚本生成的运行清单与启动提示；
3. 没有指定时为 `GENERAL`。

必须同时在两个位置注入专用身份：

- 结构化运行清单；
- Agent 启动提示词。

入口文档再要求 Agent 核对两者，减少因某个 CLI 是否自动读取特定文件而产生的
歧义。

出现以下情况必须停止：

- 运行清单写 `IMPLEMENTER`，提示词却写 `REVIEWER`；
- 角色存在但任务 ID 或提交边界缺失；
- 审查角色没有只读权限；
- Agent 被要求在同一进程中先实现再切换为审查；
- 所有者最新指令与自动任务冲突。

Agent 不能用“我通常是 Codex/Claude”覆盖本次显式角色。

---

## 5. 执行器适配层

## 5.1 适配层的职责

每个执行器适配器只做四件事：

1. 接收角色、模型、effort、提示文件和输出文件；
2. 选择该角色的 CLI 权限配置；
3. 禁止会话持久化和交互批准；
4. 把进程退出码与最终输出交还中立包装器。

适配器不决定项目目标、不推进轮次、不创建 Git 提交。

## 5.2 能力矩阵

项目应维护实际能力矩阵，而不是假定完全一致：

| 能力 | Claude 类执行器 | Codex 类执行器 |
| --- | --- | --- |
| 模型选择 | `--model` | `--model` |
| 推理强度 | `--effort` | 配置或对应参数 |
| 非交互 | `dontAsk` | `approval_policy=never` |
| 实现权限 | 工具 allow/deny | workspace-write sandbox |
| 审查权限 | 无 Write/Edit 的工具集 | read-only sandbox |
| 新会话 | no session persistence | ephemeral |
| 最终报告 | stdout/指定文件 | output-last-message |

表格是逻辑示例，实际参数必须以当前 CLI 能力为准，并通过预检和静态测试验证。

## 5.3 不能抽象掉的差异

如果某执行器无法可靠提供只读模式，就不能把它配置为无人值守 REVIEWER；如果它
无法安全写项目工作区，就不能作为 IMPLEMENTER。适配器应明确失败，而不是降低角色
契约来“兼容”。

---

## 6. 运行配置与调用清单

## 6.1 默认策略

版本化的运行配置可以保存：

```dotenv
IMPLEMENTER_AGENT=claude
IMPLEMENTER_MODEL=sonnet
IMPLEMENTER_EFFORT=high
IMPLEMENTER_TIMEOUT_SECONDS=7200
REVIEWER_AGENT=codex
REVIEWER_MODEL=gpt-5.6-sol
REVIEWER_EFFORT=high
REVIEWER_TIMEOUT_SECONDS=3600
AGENT_HEARTBEAT_SECONDS=30
AGENT_TERMINATION_GRACE_SECONDS=15
```

这些值是“默认调用策略”，不是角色定义。所有者可以在一次父脚本调用中覆盖，而
不修改仓库默认值。

## 6.2 每次调用的运行清单

清单至少包含：

```dotenv
RUN_ID=...
TASK_ID=...
ROUND=1
ROLE=IMPLEMENTER
EXECUTOR=claude
MODEL=sonnet
EFFORT=high
PERMISSION_PROFILE=workspace-write-no-git
TIMEOUT_SECONDS=7200
BASE_COMMIT=...
TARGET_COMMIT=PENDING
EXPECTED_OUTPUT=.agent/implementation-report.md
STARTED_AT_UTC=...
```

运行清单应：

- 存放在被 Git 忽略的 artifacts 目录；
- 使用经过校验的惰性字符串，不作为 shell 配置执行；
- 在简报中可追溯；
- 不包含密钥、令牌或完整环境变量。

正式实现/审查报告也要记录实际执行器、模型和 effort。这样即使 artifacts 被清理，
Git 中仍保留关键审计信息。

## 7. 中立父脚本与状态机

父脚本不是第三个决策 Agent，而是确定性的流程控制器。

推荐状态：

```text
READY
  ↓
IMPLEMENTING
  ↓
IMPLEMENTATION_CHECKPOINTED
  ↓
REVIEWING
  ├─ PASS → COMPLETE
  └─ CHANGES_REQUIRED → NEEDS_CHANGES → 下一轮 IMPLEMENTING
```

任何阶段还可以进入 `STOPPED`，原因包括权限、认证、额度、超时、脏工作区、越权、
报告无效或所有者决策。

父脚本需要负责：

- 获取全局循环锁；
- 解析并校验两种角色配置；
- 完成 CLI 登录、MCP、权限、依赖和 Git 预检；
- 生成运行清单；
- 监管子进程、心跳、超时和进程组终止；
- 检查实现者没有控制 Git 或修改控制面；
- 运行统一验证；
- 创建本地实现检查点；
- 启动新的只读审查进程；
- 校验 VERDICT 与固定报告章节；
- 归档报告并创建本地审查检查点；
- 生成各轮简报；
- 达到终止条件时把控制权交还所有者。

父脚本不应：

- 在后台同时运行实现者和审查者；
- 自动扩展目标；
- 自动 push 或部署；
- 在失败后无限重试；
- 用宽泛权限掩盖适配器问题；
- 删除未知未提交修改。

## 8. 同一种执行器承担两种角色

这是允许的配置，但必须明确其含义。

### 可以获得的独立性

- 不同进程；
- 不同角色提示；
- 不同权限；
- 无会话继承；
- 审查只依据提交、diff、报告和验证证据。

### 不能获得的独立性

- 不同模型家族的认知多样性；
- 不同供应商实现带来的交叉验证；
- 完全消除相同系统性偏差。

因此，简报应标明：

```text
IMPLEMENTER: codex / model-X / high
REVIEWER: codex / model-X / high
```

对于高风险项目，仍可规定实现者与审查者不得使用同一模型或同一供应商；这是项目
风险政策，不应写死在通用元方法中。

---

## 9. 权限设计

权限遵循“角色所需最小能力”，不是“Agent 值不值得信任”。

### IMPLEMENTER

通常需要：

- 读取项目；
- 写源代码、测试和实现报告；
- 运行构建、测试、本地预览；
- 访问公开技术资料和浏览器验证。

通常不需要：

- Git stage/commit/push；
- 修改 refs、hooks 和 Git 配置；
- 修改角色、审查、权限和轮次控制面；
- sudo、系统目录、密钥存储和完整环境变量；
- 启动子 Agent。

### REVIEWER

通常只需要：

- 读取提交、diff、规范、代码、测试和 artifacts；
- 运行不改变仓库的检查；
- 使用浏览器与公开资料；
- 输出一个候选 Markdown 报告。

审查报告写入版本库的动作仍由外层脚本完成。

### 无人值守

无人值守进程必须：

- 关闭交互式 stdin；
- 使用 `never`/`dontAsk` 等不等待批准的模式；
- 缺权限时明确失败；
- 由父脚本分类并记录失败；
- 不因无人看守而扩大机器权限。

## 10. Git 与证据

推荐每轮形成两个本地提交：

```text
agent: implementation round N
agent: review round N
```

提交标题只表达阶段，不绑定执行器。实际执行器写进报告和运行清单。

实现检查点至少包含：

- 实现修改；
- 相关测试和必要的当前事实更新；
- 实现报告；
- 上一实现运行配置状态。

审查检查点至少包含：

- 最新正式审查；
- 新的历史归档；
- 轮次与结论状态；
- 审查运行配置状态。

父脚本必须拒绝：

- 启动前脏工作区；
- Agent 改写 Git 历史或 refs；
- 实现者预先 stage；
- 审查后出现报告范围外的仓库修改；
- 覆盖已有历史审查。

---

## 11. 报告与简报

## 11.1 实现报告

至少包括：

- 本轮目标；
- 实际运行配置；
- 修改内容与原因；
- 已处理审查编号；
- 验证命令和真实状态；
- 浏览器证据；
- 未解决风险和近似；
- 基准与结果边界；
- 下一位 REVIEWER 的检查重点。

## 11.2 审查报告

至少包括：

- 实际运行配置；
- 目标提交和对比基准；
- 验证结果；
- `PASS` 或 `CHANGES_REQUIRED`；
- 按严重等级组织的问题；
- 每个问题的要求、证据、影响、复现、预期/实际和验收条件；
- 已确认内容与未验证区域。

## 11.3 多轮简报

所有者不应被迫逐个阅读 Git diff。循环结束后生成简报，按轮列出：

- 实现者实际配置、提交、主要改动和验证；
- 审查者实际配置、结论和问题标题；
- 停止原因；
- 下一步建议；
- 深入查看报告和提交的命令。

简报是索引，不取代原始证据。

---

## 12. 终止条件

满足任一条件即停止：

- `VERDICT: PASS`；
- 达到 `MAX_ROUNDS`；
- 连续两轮出现同一未解决的 Blocker/Major；
- 需要所有者作产品或技术取舍；
- 需要凭据、付款、外部授权或部署；
- CLI 认证、额度、MCP 或浏览器环境失败；
- 关键验收无法可靠验证；
- 工作区或 Git 状态不安全；
- Agent 越权或报告格式失效；
- 父脚本无法确认当前子进程已经结束。

停止不是失败；它表示自动化边界已到，决策权回到人。

```text
├── README.md
├── roles/

├── next-task.md
├── runtime.env
├── state.env
├── implementation-report.md
├── latest-review.md
├── review-history/
└── artifacts/
    ├── runs/
    ├── implementation/
    ├── review/
    ├── validation/

├── run-review.sh
├── run-validation.sh
├── generate-cycle-summary.sh
├── test-agent-runtime.sh
├── agent-runners/
│   ├── claude.sh
│   └── codex.sh
└── lib/
    └── agent-runtime.sh
```

执行器入口文件应保持薄，不复制完整角色职责。这样新增执行器时只需增加入口和
适配器，不需要复制整个项目方法。

## 14. 建立一个新项目

### 阶段 A：建立事实与目标

1. 建立 `PROJECT.md`；
2. 建立唯一正式规格 `PROJECT_SPEC.md`；
3. 把工程细节放入专门设计文档，不把口号堆进目标；
4. 明确本阶段不做什么。

### 阶段 B：建立身份系统

1. 写 `AGENT_PROTOCOL.md`；
2. 写 GENERAL、IMPLEMENTER、REVIEWER 契约；
3. 把各 CLI 入口改成薄引导；
4. 规定身份分配优先级和冲突停止规则。

### 阶段 C：建立适配器

1. 列出计划支持的执行器；
2. 为每个执行器实现角色权限映射；
3. 验证非交互、无会话继承和最终输出；
4. 对无法满足角色安全要求的组合明确禁用。

### 阶段 D：建立父脚本

1. 配置解析与覆盖；
2. 串行状态机与全局锁；
3. 预检、心跳、超时和停止分类；
4. 实现边界机械检查；
5. 审查报告校验和归档；
6. 最大轮数与简报。

### 阶段 E：模拟后再实跑

先完成：

- shell 语法；
- 配置合法/非法矩阵；
- 同执行器双角色路由；
- 交换角色路由；
- 假子进程成功、失败和超时；
- 陈旧锁与活动锁；
- 运行清单字段；
- 脏工作区拒绝；
- 不启动真实 Agent 的预检。

再由所有者在干净工作区启动第一轮真实 cycle。

## 15. 从 v2.0 迁移到 v3.0

1. 保留 v2.0 作为历史，不直接覆盖；
2. 找出所有“Claude=实现者、Codex=审查者”的文档和脚本；
3. 新增统一身份协议和 GENERAL；
4. 把实现/审查职责移动到品牌无关的角色文件；
5. 把 `AGENTS.md`、`CLAUDE.md` 改成薄执行器入口；
6. 将 `CLAUDE_MODEL` 等配置迁移为 `IMPLEMENTER_*`、`REVIEWER_*`；
7. 增加每种 CLI 的适配器；
8. 父脚本接受显式执行器、模型与 effort；
9. 提交标题改为角色阶段，报告记录实际运行者；
10. 预检默认、交换和同执行器三种组合；
11. 不改变当前业务任务 ID、轮次和状态；
12. 在真实循环前建立一次基础设施提交。

迁移完成的判定不是“文档改了名字”，而是以下命令路径都能被静态验证：

```text
Claude IMPLEMENTER → Codex REVIEWER
Codex IMPLEMENTER → Claude REVIEWER
Codex IMPLEMENTER → Codex REVIEWER
Claude IMPLEMENTER → Claude REVIEWER
```

它们不一定都适合某个项目，但身份系统不应在结构上阻止。

## 16. 常见反模式

### 反模式一：品牌即身份

换模型就必须重写职责文档，说明角色没有真正抽象。

### 反模式二：所有 Agent 都是通用帮手

没有差异化交付与责任边界，多 Agent 只增加理解和协调成本。

### 反模式三：GENERAL 等于全权

默认身份只是没有专用流程职责，不代表可以越过所有者范围和安全规则。

### 反模式四：同一进程先实现再审查

这不是独立审查。必须结束实现进程，再以新提示、只读权限和无会话继承启动审查。

### 反模式五：强行统一 CLI 参数

角色目标应统一，具体权限机制必须按执行器真实能力适配。

### 反模式六：Agent 相互启动

会产生重叠、父子关系混乱和无法可靠判断完成。中立父脚本应拥有唯一调度权。

### 反模式七：给无人值守 Agent 机器级全权

权限问题应在项目级适配器中最小修复，不能用 sudo、全盘访问或交互 bypass 掩盖。

### 反模式八：只有 Git 历史，没有简报

提交是证据库，不是所有者的日常阅读界面。每个有限循环应生成可快速理解的报告。

### 反模式九：无限循环

如果三轮仍不能收敛，通常需要拆任务、补资料、调整模型或由人作决定。

## 17. 方法有效性的检查问题

一个项目真正采用 v3.0，应能回答：

1. Agent 未被指定角色时是谁？
2. 本轮谁是 IMPLEMENTER，谁是 REVIEWER？
3. “谁”指角色、执行器还是模型？
4. 每个执行器怎样落实只读或可写权限？
5. 同一执行器双角色时如何隔离上下文？
6. 父脚本怎样知道当前 Agent 已结束？
7. 实际运行配置在哪里审计？
8. 谁拥有 Git 提交、push 和部署权？
9. 达到什么条件自动停止？
10. 所有者怎样在一分钟内看懂三轮发生了什么？

任何答案只能靠“大家应该知道”或聊天上下文维持，都说明控制面仍不完整。

## 18. 最终公式

v1.0 的基本思路是：

```text
人 + 多个相似帮手
```

v2.0 的改进是：

```text
人定目标 + 实现者 + 独立审查者 + 有限父循环
```

v3.0 的完整形式是：

```text
人拥有目标与决策
+ 默认 GENERAL 协作
+ 品牌无关的 IMPLEMENTER / REVIEWER 角色契约
+ 可替换执行器及其安全适配层
+ 显式模型、effort、权限与任务边界
+ 严格串行、可审计、有限且可停止的父流程
```

多 Agent 的价值不来自数量，而来自职责差异、上下文隔离、可验证交接和可控自动化。
角色必须稳定，执行器必须可替换，权限必须按角色收敛，最终决定权必须始终在人。
