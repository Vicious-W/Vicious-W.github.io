# FLY 统一物理引擎工程基线

DESIGN_STATUS: ACTIVE

本文件定义《FLY》的统一仿真架构、大气与世界坐标、飞行器接口、首个热气球模型、
气象扩展方式、工程近似和验证不变量。体验状态、场景选择和资源生命周期见
`FLY_SCENE_ARCHITECTURE.md`；当前产品边界和最终验收优先以 `PROJECT_SPEC.md` 为准。

## 1. 设计原则

《FLY》不是“物理库 + 天气特效 + 飞行器动画”的拼接。它只有一个权威世界：

```text
输入事件（带时间戳）
        ↓
固定时间步调度器
        ↓
逻辑世界坐标 / 大气与气象场
        ↓
飞行器热力、推进、气动力与控制
        ↓
刚体、约束、接触与结构载荷
        ↓
权威状态快照
   ├─ 渲染插值
   ├─ 相机
   ├─ 音频参数
   ├─ 粒子与体积光学
   └─ 测试/调试观测
```

锁定规则：

- 只有固定时间步推进权威物理；渲染帧不得直接改变物理状态；
- 模块之间交换有单位的状态、力、力矩、能量、质量流或事件；
- 视觉和音频只能读取结果，不得反向伪造升力、湍流、燃料或碰撞；
- 允许不同更新频率，但所有采样必须对应明确仿真时间；
- 一个飞行器在任一时刻只能由一个刚体/动力学状态拥有者控制；
- 复杂性通过模块边界管理，不建立一个包含全部逻辑的巨型 `physicalScene.js`。

## 2. 真实性标签

每个飞行器、气象和世界参数必须使用以下标签之一：

- `PRIMARY_SOURCE`：直接来自 FAA、NASA、NOAA、制造商手册、型号证书或同等级资料；
- `DERIVED`：由一手数据进行单位换算或公式推导，记录输入和公式；
- `ENGINEERING_PROXY`：浏览器实时计算所需的可解释近似，记录单位、范围和影响；
- `ART_DIRECTION`：所有者规定的视觉或体验方向，不冒充现实事实；
- `FICTIONAL_MODEL`：UFO 等虚构系统，记录自洽规则和与现实物理的分界。

没有来源的数值不能伪装成真实型号参数。缺失资料时可以采用代理，但必须在模型清单、
测试和实现报告中明确标记。

## 3. 单位、坐标与时间

### 3.1 单位

- 长度：米；
- 时间：秒；
- 质量：千克；
- 温度：开尔文；
- 压力：帕；
- 速度：米/秒；
- 力：牛顿；
- 力矩：牛顿·米；
- 能量：焦耳；
- 功率：瓦；
- 燃料：千克，显示层可以转换为体积。

Three.js、刚体引擎、天气场和测试不得分别使用未标记的英尺、厘米或“场景单位”。
官方英制参数在载入 vehicle manifest 时转换，并保留原值与来源。

### 3.2 坐标

- 逻辑世界使用右手坐标，`+Y` 向上；水平平面为 `X/Z`；
- `WorldPosition` 由整数区块坐标和区块内双精度位置组成；
- Three.js 与活动物理域使用相对当前浮动原点的局部米制坐标；
- 海拔以平均海平面代理面为零；地面高度由区块地形查询；
- 重力首阶段可取局部恒定向量，进入近空间/轨道阶段前必须升级为球形地球重力；
- 经度、纬度和完整地球曲率不属于第一阶段，但远景地平线不得表现为近距离直立幕布。

### 3.3 固定时间步

建议权威物理步长 `dt = 1/120 s`；若实现阶段通过稳定性测试证明 `1/60 s` 足够，可以
记录理由后采用。调度器必须：

1. 用真实帧时间填充 accumulator；
2. 每帧最多执行有界子步，避免标签页恢复后的“死亡螺旋”；
3. 超出上限的真实时间按明确策略丢弃或暂停，不一次补算数分钟；
4. 保存前后两个权威快照供渲染插值；
5. 输入按仿真时间消费，同一控制时间线不随刷新率改变；
6. 天气宏观场可低频更新，飞行器每个物理步都从时间插值后的场采样。

## 4. 权威状态和模块接口

建议的逻辑接口不是强制语法，但语义必须保留：

```js
atmosphere.sample(worldPosition, simTime) => {
  temperatureK,
  pressurePa,
  densityKgM3,
  humidity01,
  windVelocityMps,
  turbulenceVelocityMps,
  precipitationKgM2s,
  liquidWaterKgM3,
  electricFieldVm
}

vehicle.step({ dt, atmosphere, gravity, controls, terrainQuery })
world.shiftOrigin(newOrigin)
world.getSnapshot(alpha)
```

权威 `FlyWorldState` 至少包含：

- `simTime`、随机种子、当前浮动原点和已加载区块；
- 标准大气基线与当前天气系统；
- 活动飞行器的世界/局部位置、姿态、线速度和角速度；
- 飞行器质量清单、推进/热力/燃料/结构/接触状态；
- 当前控制所有者 `MANUAL | AUTO_RECOVERY | NONE`；
- 相机模式，但相机不能拥有飞行器物理；
- 音频是否由用户手势解锁；
- 旅程阶段与恢复状态。

渲染对象的 position、动画 mixer 时间、粒子年龄或 Web Audio 节点值不是权威业务状态。

## 5. 大气模型

### 5.1 标准基线

基础大气采用 U.S. Standard Atmosphere 1976 的分层温度、压力和密度关系。第一阶段
至少正确覆盖对流层：

```text
T(h)   = T0 + L · h
p(h)   = p0 · (T(h) / T0)^(-g / (L · R))     L != 0
rho(h) = p(h) / (R · T(h))
```

实际实现需使用标准中对应分层和符号约定，不能把上式机械扩展到所有高度。首阶段常数
从正式标准读取；NASA 给出的海平面典型状态可用于交叉检查，而不是另建第二套密度表。

### 5.2 天气扰动

天气系统在标准基线上定义连续的三维/时间场：

- 温度偏差；
- 压力偏差或可推导的压力梯度；
- 水汽/湿度；
- 大尺度背景风；
- 阵风、热对流、机械湍流和风切变；
- 云水、降水和电荷（后续天气）。

密度必须由最终温度、压力和湿空气近似统一推导，不能同时手工动画密度。风场返回空气
相对地面的速度；飞行器气动力使用：

```text
v_air = v_body_world - v_wind_world
```

当飞行器与周围空气同速时，气动阻力趋近零；不能继续根据地速播放强风或施加阻力。

### 5.3 晴空第一阶段

第一阶段天气不是完全静止的蓝色背景，至少由以下状态组成：

- 随高度变化的平均风向与风速；
- 长时间尺度、低幅度阵风；
- 由地表受热差异生成的有限范围热气流柱；
- 热气流周边的补偿下沉；
- 与地形粗糙度相关的近地机械湍流；
- 稀疏、体积化的晴空积云代理，可由局部湿度/上升气流决定密度和消散；
- 能见度和大气散射随光程、高度、太阳方向连续变化。

随机扰动必须使用带时间连续性的确定性噪声或涡旋模型；每帧独立随机力会制造高频
抖动，不属于湍流模型。

## 6. 程序化无限世界

### 6.1 区块

- 每个区块由 `worldSeed + integerChunkCoordinate` 确定；
- 地形高度、地表类型、海陆、植被/建筑障碍和可降落元数据来自同一生成结果；
- 相邻区块共享边界采样，不能出现裂缝、法线断层或碰撞高度不一致；
- 区块有生成、激活、降级、回收四个明确阶段；
- 只在飞行器预测航迹前方预取，不能无限保留已经远离的实例和纹理。

第一阶段世界应包含可辨认的田野、缓坡、稀疏树林、道路、水面和远方起伏，给高度、
速度与降落判断提供参照。它不是完整步行开放世界；只有降落可能接触的近场对象需要
高精度碰撞。

### 6.2 浮动原点

达到阈值后，在一个物理步边界执行原点迁移：

1. 选择新的逻辑原点；
2. 对全部局部物理体、渲染对象、相机、音源和活动粒子应用同一平移；
3. 不改变逻辑世界坐标、线/角速度、力、温度、燃料、随机流场相位和飞行阶段；
4. 清空或重建依赖绝对局部坐标的 broadphase 缓存；
5. 记录迁移事件供测试。

迁移不能在渲染中被看到或听到。候选着陆点和风场必须以逻辑坐标存储，不能在迁移后
跳到另一位置。

### 6.3 局部物理域

- 飞行器始终处于高精度活动域；
- 预测碰撞和着陆范围内的地表、树木、建筑与障碍生成碰撞代理；
- 远景对象只渲染，不加入刚体世界；
- 物体进入/离开活动域时要保持逻辑身份，不得因为 LOD 切换改变可见位置；
- “安全着陆”查询必须读取与实际碰撞几何相同的数据。

## 7. 飞行器插件边界

所有飞行器共享：

- 仿真时钟和重力；
- 大气/天气采样；
- 世界坐标和区块；
- 刚体、接触和资源生命周期；
- 输入动作层、相机接口、音频事件总线和测试快照。

每类飞行器独立实现：

- 质量、惯性和部件拓扑；
- 空气动力/浮力；
- 推进和能源；
- 操纵机构、控制律和联锁；
- 结构载荷、损伤与失效；
- 自动安全结束策略；
- 型号操作指南。

禁止在公共接口中提供 `moveForward`、`moveUp`、`turnLeft` 之类直接改写位姿的万能
飞行方法。公共输入应表达物理动作，如 throttle、burner valve、elevator、collective、
vent 或 reaction-control command。

## 8. 第一飞行器参考构型

### 8.1 Cameron C-100 包络

制造商 C-Type 页面提供：

| 参数 | 官方值 | 工程使用 |
| --- | --- | --- |
| gores | 16 | 建立 16 个真实纵向分片和承力拓扑 |
| 体积 | 100,000 ft³ | `DERIVED ≈ 2,831.68 m³` |
| 高度 | 65 ft | `DERIVED ≈ 19.812 m` |
| 直径 | 57 ft | `DERIVED ≈ 17.374 m` |
| certified weight | 2,000 lb | 认证上限字段，不当作包络或实际总质量 |
| standard envelope weight | 218 lb | `DERIVED ≈ 98.9 kg` 包络基线 |

官方还列出 Nomex 口部面板、悬挂索、deflation line、parachute、内部水平承力带和
平滑锥形面板。这些是三维部件/连接依据，不是材质贴图清单。

首阶段使用 C-100 包络 + 同一制造商产品族的篮筐、框架、NEO 双燃烧器与燃料瓶作为
参考配置。除非取得飞行手册或型号兼容数据，不声称它是某个序列号航空器的精确认证
组合；具体下部质量和尺寸标记 `ENGINEERING_PROXY` 或制造商来源。

### 8.2 多体结构

最低动力学拓扑：

```text
包络气动/浮力体
   ↕ 等效柔性悬挂（轴向刚度、阻尼、摆动自由度）
燃烧器框架与燃料系统质量
   ↕ 刚性/半刚性连接
篮筐刚体 + 驾驶员/载荷
   ↕ 接触、摩擦、倾倒和拖曳
地形碰撞体
```

包络可使用一个低分辨率气动/浮力状态和高分辨率渲染网格，但受力点、压力中心、
悬挂点与可见结构要一致。逐片织物有限元不属于首阶段；等效悬挂必须允许篮筐相对
包络摆动，并把阵风和着陆冲量传递到可见绳索、声音和相机。

## 9. 热气球热力与浮力

### 9.1 质量清单

每个物理步的总质量至少为：

```text
m_total = m_envelope
        + m_basket
        + m_frame_burners
        + m_tanks
        + m_fuel
        + m_occupants
        + m_internal_air
```

燃料消耗会同时降低 `m_fuel` 和可用热功率；内部空气质量随温度和通风变化。不得把
certified weight 直接填入 `m_total`。

### 9.2 空气状态与浮力

包络开口使内部压力近似外界压力。最低模型：

```text
rho_out = atmosphere.density(position)
rho_in  = p_out / (R_air · T_in)
m_air   = rho_in · effectiveVolume
F_b     = rho_out · effectiveVolume · |g|
F_grav  = m_total · gVector
```

`effectiveVolume` 可以随包络充盈度变化；出发时已充盈但仍受地面/系留约束。净浮力是
浮力与全部重量的合力，不是 `temperature -> verticalVelocity` 的查表动画。

### 9.3 能量平衡

最低热力状态：

```text
dU/dt = etaBurner · mdotFuel · LHV
      - hA · (T_in - T_out)
      - epsilonSigmaA · (T_in^4 - T_out^4)
      - Q_vent
      - Q_openMouthExchange
```

- 燃烧器阀门控制 `mdotFuel`，燃料不足时为零；
- `etaBurner`、换热系数、有效面积和辐射率必须有来源或代理标签；
- vent 增大热空气/焓流出，关闭后不能立即把温度恢复；
- 包络最高温度要有型号/材料限制；超过限制时首阶段至少限制继续加热并产生明确警告，
  后续可加入材料损伤；
- 主燃烧器与 whisper burner 若分别实现，必须有不同燃料流、热功率和声音状态，不能
  只换音色。

为了浏览器实时性，可以使用均匀内部温度的 lumped model。它是明确的
`ENGINEERING_PROXY`；未来需要热分层时扩展为多个垂直温度节点，不能暗称首阶段已求解
完整内部流体。

## 10. 气动力、悬挂和地面接触

每个主要空气动力体使用相对空气速度：

```text
F_drag = -0.5 · rho · Cd · Aref · |v_air| · v_air
```

- 包络、篮筐和悬挂可使用不同 `Cd`、参考面积和受力中心；
- 角阻尼来自空气动力矩和悬挂，不直接把角速度每帧乘任意常数；
- 热气流、阵风和风切变通过局部风采样自然改变各受力点；
- 篮筐接地使用真实法向、摩擦和恢复系数；
- 高水平速度着陆可以拖曳、倾斜或弹跳；自动系统应尽量降低下降率并选择合适地表，
  但不能覆盖接触求解结果；
- 包络与地形的完整柔体接触属于后续；首阶段至少有卸载/倒伏代理，不能让包络穿入
  地面后继续保持飞行形态。

## 11. 控制权与自动安全降落

控制权状态：

```text
NONE → MANUAL → AUTO_RECOVERY → RECOVERED
                  ↘ MANUAL（用户明确取消且仍安全时）
```

MANUAL 只控制物理部件：主燃烧器阀、可选 whisper 阀、顶部 vent。用户通过高度选择
不同风层影响航迹，没有直接水平操纵。

AUTO_RECOVERY 的规划循环：

1. 在当前航迹与可用燃料范围内查询候选着陆地表；
2. 排除水面、陡坡、树木/建筑/线路密集区和区块边缘不确定区；
3. 用当前垂直控制能力和分层风场预测多个轨迹；
4. 选择具有余量的候选点；
5. 只通过燃烧器和 vent 命令控制高度；
6. 每次天气/可达性显著变化时重规划；
7. 接地、停止危险拖曳、燃烧器关闭并卸载包络后进入 RECOVERED。

规划器可以用简化预测模型，但实际飞行仍由权威物理求解。规划器不得设置位置、速度、
姿态或临时关闭风场/碰撞。

## 12. 视觉、声音和触觉代理

- 包络鼓胀、局部皱褶和绳索张力读取充盈、载荷和相对运动；
- 火焰长度、颜色、光照和热扰动读取燃料流与热功率；
- 地面移动、云影和地平线视差提供速度/高度线索；
- 风声使用相对空气速度和相机所在空间；
- 燃烧器声源附着实际燃烧器，并由阀门和燃料状态启动/停止；
- 织物拍动和悬索声音来自张力变化或低充盈/阵风事件；
- 篮筐接触声来自接触冲量、切向速度和地表材料；
- 自动降落不播放独立“成功音效”代替真实接地声，可以在 RECOVERED 后提供非文字
  状态反馈；
- 音频必须限流、限峰值并在用户手势前保持锁定。

## 13. 后续气象扩展

后续天气共享相同 atmosphere field，不创建独立天气动画世界：

### 多云

- 湿度、凝结层、体积云密度、上升/下沉气流、能见度和云影耦合；
- 穿云影响光学、湿度、风和声音，而不是只叠加白色雾。

### 雷暴

- 对流单体按发展、成熟、消散阶段演化；
- 成熟阶段同时存在上升气流、降水下沉、阵风锋、湍流、电荷和闪电；
- 闪光先照亮真实云体，雷声按声速和距离延迟；
- 不把闪电直接瞄准玩家，也不把屏幕抖动当作湍流。

### 台风

- 由移动低压中心、三维旋转风场、眼、眼墙、螺旋雨带、边界层湍流和海面响应组成；
- 眼墙拥有最强风和深对流，风速不能只用距离中心的单一线性函数；
- 进入眼区后风雨暂时减弱，穿过另一侧眼墙时风向和载荷变化连续；
- 全球尺度台风使用参数化/多尺度场是 `ENGINEERING_PROXY`，不能声称实时求解完整
  数值天气预报模型。

## 14. 后续飞行器扩展

- 固定翼：机翼/尾翼分布受力、迎角、升阻系数、失速、舵面、推进和重心；
- 喷气式：发动机转速/推力动态、燃料、进气条件、可压缩性代理和高速气动；
- 旋翼：旋翼盘、诱导流、扭矩、collective/cyclic、尾桨或反扭矩系统；
- 航天飞机：再入能量、气动加热、高迎角、高速气动和无动力进近，不能像普通飞机
  从跑道动力起飞；
- UFO：单独 `FICTIONAL_MODEL`，记录推进作用点、能源、最大加速度、惯性补偿边界和
  失效方式。

这些类别只共享世界和接口，不共享热气球的浮力/燃烧模型。

## 15. 性能策略

- 近场物理、远景渲染和天气宏观场使用不同更新预算；
- 区块生成分帧或放入 Worker 时，提交结果必须带世界种子和坐标，不能改变确定性；
- 使用对象池、实例化和 LOD 控制地表/植被/云的分配；
- 体积云和大气允许随设备能力调整采样质量，但密度场和天气状态不因画质改变；
- 降级首先减少远景采样、阴影和粒子，不减少物理步或改变飞行器受力；
- 调试接口暴露计时、活动区块、刚体数、原点迁移、天气采样和飞行器状态，但不得在
  普通页面显示文字。

## 16. 验证不变量

最低自动测试：

- 标准大气在首阶段高度范围内温度/压力/密度连续且随高度趋势正确；
- 相同种子、位置和时间返回相同世界/风场采样；
- `v_body == v_wind` 时气动阻力接近零；
- 燃烧器热输入、温度、内部密度、净浮力的因果方向正确；
- vent 使能量/热空气减少，不直接设置下降速度；
- 燃料质量单调且守恒到允许误差；
- 悬挂系统不凭空产生总动量，静止状态可收敛；
- 不同渲染帧序列下同一输入时间线结果接近；
- 原点迁移不改变逻辑状态和相对几何；
- 区块生成边界连续，回收后活动对象数有界；
- AUTO_RECOVERY 只产生合法控制命令，从不写位姿；
- 场景 dispose 后仿真时钟、输入、音频和区块任务停止。

浏览器证据至少包括：手动离地、升降、跨风层漂移、一次原点迁移、自动寻找着陆区、
真实接地、三视口输入和 SOURCE 往返回归。

## 17. 当前差距

- C-100 包络数据已锁定；完整篮筐、框架、燃烧器、燃料瓶组合仍需在实现清单中逐项
  绑定制造商资料，首阶段不得声称是认证序列号复刻；
- 热损失、燃烧效率、阻力系数、悬挂刚度和阻尼需要由手册、实验资料或显式校准代理
  确定；
- 首阶段均匀内部温度不能表达完整垂直热分层；
- 程序化地表是可解释的世界代理，不对应现实具体地点；
- 稀疏晴空云是湿度/气流驱动的体积代理，不是实时微物理云模型；
- 完整织物撕裂、索具失效、火灾和人员伤害不属于首阶段。

实现报告必须保留这些差距，不能因为画面完成而把它们写成已解决。
