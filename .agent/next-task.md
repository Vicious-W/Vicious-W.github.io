  或台风；
- 首个包络几何采用 Cameron C-100 官方规格；下部系统未被完整型号资料覆盖之处必须

## Owner hands-on priorities for rounds 5-6

所有者在第四轮实现后实际游玩了 FLY，并确认基础流程已经存在，但整体仍显原始。第五、
六轮必须先把以下体验问题当作当前任务的高优先级验收项，而不是只继续补底层接口：

1. 热气球的控制必须方便、可发现且可验证。指南应把每个实际可用输入与画面中的物理
   控制件明确对应；鼠标、触控与键盘路径都应能够真正触发同一权威动作状态。
2. 篮筐内 PILOT 视角需要重新校准：位置、朝向、近裁剪面、视野、环视范围和运动响应
   应提供稳定地平线、可辨认的篮筐/燃烧器参照与舒适观察，不能穿模或让用户失去方向。
3. 页面上出现的每个控制图形都必须具有清楚、无文字也可理解的视觉反馈；若它表示操作，
   就必须能被鼠标、触控及适用的键盘方式激活。不可操作的装饰不得伪装成按钮。
4. 风景和天气系统与飞行器同为 FLY 的核心。当前阶段仍只交付晴空，不提前用浅层占位
   扩张到多云、雷暴或台风；但晴空的大气、云、光照、能见度、风、热气流、地貌、水体、
   植被与尺度感必须形成可信、连续、由统一世界状态驱动的视觉和物理环境。
5. 本轮改进必须通过真实浏览器旅程检查，而不只依赖逻辑测试；尤其验证可点击性、三种
   相机、手动升降、环境可读性、视口适配以及控制说明是否与实际行为一致。

审查者应首先确认第四轮是否满足这些可玩性要求，再将具体阻塞项交给第五轮；第五轮后的
审查继续以同一组体验问题和原正式物理验收为依据，第六轮完成后交给所有者亲自体验。

## Required work

### 1. 多场景宿主

1. 将 `src/main.js` 改为全站 SceneHost；建立场景注册、生命周期、输入路由、音频门和
   资源 scope。
2. 为 SOURCE 增加最小生命周期适配和幂等 dispose；不得重写 SOURCE 业务。
3. 建立无文字三维 SITE_SELECT，使用轻量 SOURCE 与 FLY 缩影，支持指针、触控、键盘
   选择和 `Escape` 返回。
4. 任意时刻只运行一个业务场景；切换时完整清理 RAF、监听器、音频、物理与 GPU 资源。

### 2. FLY 配置和指南

1. 建立 weather/vehicle registry，第一阶段只注册 `clear` 和 `hotAirBalloonC100`。
2. 配置空间以三维 C-100 预览和实时晴空反馈表达选择，不用文字菜单。
3. 建立唯一允许说明性文字的型号指南，明确 `Space` 主燃烧器、`V` 顶部 vent、`R`
   自动安全降落、相机控制，以及“水平方向来自不同高度风层”。
4. 指南支持桌面、触控与键盘；飞行中重开指南时暂停物理并清零持续控制。

### 3. 统一物理基础

1. 建立固定时间步、accumulator、有界追帧、快照插值和带时间戳动作输入。
2. 建立逻辑世界坐标、局部活动域、确定性种子、区块生成/回收和浮动原点。
3. 建立 `atmosphere.sample(position,time)` 等价接口，统一返回温度、压力、密度、湿度、
   风、湍流、降水等状态。
4. 标准大气与风场、飞行器、音频和渲染只读取这一个权威世界，不建立第二套动画状态。

### 4. 晴空世界

1. 实现随高度变化的标准大气、分层背景风、连续阵风、有限热气流与近地机械湍流。
2. 实现确定性程序化地表，至少包含田野、缓坡、道路、水面、稀疏树林/障碍和可降落
   元数据；近场碰撞与安全查询必须读取同一地形。
3. 实现程序化天空、大气散射、太阳、地平线、能见度和稀疏体积晴空积云；不用照片、
   天空盒图片或平面云片承担主要环境。
4. 区块持续前向生成并回收后方资源；飞行中至少能触发一次不可感知的原点迁移。

### 5. C-100 参考热气球

1. 按 16 gores、100,000 ft³、65 ft 高、57 ft 直径建立包络；分别建模 parachute/
   deflation vent、承力带、Nomex 口部、悬挂、框架、双燃烧器、两只燃料瓶、软管、
   控制绳和有壁厚篮筐。
2. 建立质量清单并区分包络自重、实际总质量与 certified weight；每个代理值有来源标签。
3. 建立内外空气状态、燃烧器燃料/热输入、热损失、vent、内部密度、浮力和重力；
   不把输入直接映射为速度。
4. 建立包络/篮筐的相对运动、等效悬挂、风阻、阵风响应、地面接触、离地和着陆。
5. 水平运动只来自相对空气速度和风场；不同高度风层能够产生不同航迹。
6. 燃料质量单调减少，燃尽后热功率、火焰和燃烧器声必须停止。

### 6. 手动旅程与自动降落

1. 旅程从已充盈、篮筐着地、燃烧器关闭的田野开始；用户真实加热后才离地。
2. 用户可以通过燃烧、自然冷却与 vent 完成上升、近似平飞和下降。
3. 默认 PILOT 视角，同时提供 CHASE/ORBIT；相机切换不改变物理。
4. `R` 或三维回收控制件进入 AUTO_RECOVERY；规划器根据分层风、地形、障碍、下降率
   和燃料选择候选点，只输出合法 burner/vent 命令。
5. 真实接地、稳定、关闭燃烧器和包络卸载后才进入 RECOVERED。

### 7. 状态声音与清理

1. 音频只在用户确认出发的手势后解锁；
2. 燃烧器、相对风、织物/悬挂和篮筐接触使用独立状态声源；
3. 预览音频、旅程音频和 SOURCE 音频不得叠加；dispose 后全部停止；
4. 视觉火焰、织物响应和落地反馈与对应状态同步，不用循环特效冒充。

## Implementation order and usage discipline

按以下顺序推进，并在每个阶段先运行相关确定性测试再扩大范围：

1. SceneHost + SOURCE 适配与往返资源测试；
2. FLY session + fixed-step + atmosphere/world interfaces；
3. 确定性区块、浮动原点和晴空环境；
4. C-100 几何、质量、热力、浮力和多体运动；
5. 指南、输入、相机、自动降落与音频；
6. 三视口完整旅程和 SOURCE 回归。

不要在早期反复进行高成本全浏览器视觉检查；先用 Node 测试关闭状态和数值不变量，
各系统连通后再完成 Playwright MCP 端到端验证。不得为了节省用量跳过最终真实浏览器
旅程，也不得提前开发非目标天气和飞行器。

## Quantitative acceptance

- C-100 关键几何与官方值一致，公制转换误差不超过 0.5%；
- 同一控制时间线在 30/60/120 Hz 渲染节奏下，物理运行 120 秒后的高度、速度、内部
  温度和燃料差异不超过实现报告声明的严格容差，目标为 1%；
- 同位置温度、压力和密度随高度连续；标准大气抽样与正式基线在目标高度范围内误差
  不超过 1%；
- `v_body == v_wind` 时平动气动阻力在浮点容差内接近零；
- 主燃烧器开启后燃料先下降、内部能量/温度上升、内部密度下降、净浮力增加；顺序
  不能由直接速度命令绕过；
- vent 开启产生相反趋势；松开后所有状态连续，无单帧温度或速度跳变；
- 没有 burner/vent 输入时持续控制值为零，blur/hidden/pointercancel 后同样为零；
- 水平飞行没有直接按键力；改变高度后，分层风可以使地面航迹方向或速度发生可测变化；
- 浮动原点前后世界位置、相对几何、速度、姿态、燃料和天气采样连续，画面位移误差
  不超过 1 CSS 像素；
- 活动区块、刚体、监听器和音频 voice 数量在长距离飞行与两次场景往返后保持有界；
- AUTO_RECOVERY 从请求到 RECOVERED 全程不直接写 position/velocity，不穿过水面、
  建筑、树木或其他已标记障碍；
- SOURCE 往返后会话重置、AUTO/MANUAL、相机、玻璃、轻水和音频仍通过原有测试。
